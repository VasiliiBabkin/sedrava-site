## Required design and implementation

### 1. Working example + exact source code **on the same page**

Implement a native, typed and security-reviewed **Sedrava docs/demo component** or \`project\` build contract. A user must see actual WebApp behaviour **directly next to or above the exact source code used to compile it**, not a screenshot or simulated widget.

Provide at least:
1. Counter: state + named action, persistence.
2. Tasks: real CRUD, search/filter, navigation, validation.
3. CRM: companies and contacts, table/dialog/theme.
4. Typed HTTP catalog: real requests to a controlled endpoint. Production live preview must have an actual permitted example API or be explicitly restricted to a CI test server; it cannot falsely show synthetic values as live remote responses.

The source panel should support syntax highlighting, line numbers (if accessible), copy, full source link, language mode/version and independent reset/reload. Show errors honestly. The demo is compiled from the same literal \`.sdr\` file as displayed; add a CI check of source hashes to prevent drift.

**Security:**
- No untrusted HTML injection, event handler strings, \`eval\` or unsanitized arbitrary script.
- The embedding primitive must be typed and same-origin/path constrained. Define CSP/frame-src and a deliberate iframe trust policy.
- Do not claim browser sandbox isolation when combining \`allow-scripts\` and \`allow-same-origin\` on a same-origin iframe. If running editable/untrusted code, isolate it on a genuinely different origin and limit permissions, or decline arbitrary code execution.
- Demo storage must not overwrite the user's main site state; show a Reset control for individual demos.
- Any eventual editor/playground must have explicit resource budgets, origin separation and no access to personal cookies/credentials. No sandbox-bypass tricks.

If the existing \`site\` compiler cannot express the demo component correctly, **extend the Sedrava compiler in its own branch and PR** with parser, AST, renderer, tests and documentation, then update this site to use the verified compiler commit. Do not solve it with a post-build HTML regex patch or hand-edited generated assets. A controlled build orchestrator combining independently compiled \`site\` and \`webapp\` output without mutating generated HTML is acceptable as a temporary staging step; release contracts must declare route ownership and collision checks.

### 2. Complete official documentation in two languages

Migrate all current \`src/content/docs/**\` pages into new Sedrava-generated site routes without losing content. At a minimum preserve:
- Getting started and setup.
- Language overview and syntax.
- Text/records/collections/navigation, using **actual** published 0.10 and experimentally available 0.11 status.
- CLI commands and examples.
- Release notes and compatibility.
- Roadmap and limitations.
- Project/dedication/source links.

Preserve existing EN/RU public URLs, locale switch links, reasonable SEO metadata, canonical and OpenGraph, sitemap, robots, image/font attribution and any current redirect requirements.

For docs rendering support **safe local Markdown or structured docs** at build time. It is fine for content to remain Markdown if the site itself is described, structured, styled and compiled through Sedrava. Implement or reuse a reviewed Markdown renderer: headings, anchors, paragraphs, lists, tables, fenced code, language labels, text emphasis, and internal links. Reject raw untrusted HTML unless explicitly reviewed. Cross-file build dependencies must be bounded and hashed.

Provide reusable **docs layout**, responsive sidebar, active section, previous/next navigation, table of contents, visible copy buttons and syntax highlighting for \`.sdr\`, shell and Python. Keep site build fully static and compatible with Nginx/FASTPANEL.

### 3. Search that works offline

Implement build-time index and local client-side full-text search across both languages, no paid API, no secret, no remote runtime request. Query must find actual text and headings in generated documentation. Display result titles and excerpts, handle Cyrillic/Latin case matching, keyboard navigation, empty/no-results, duplicates, escaping and accessibility. Keep index reasonably sized and deterministic. Verify via browser E2E.

### 4. Design

Use source-controlled tokens/styles, own font and assets with correct licenses, adaptive layout at 320/360/390/768/1024/1440 widths, sensible sticky docs navigation and accessible focus order. Maintain WCAG-oriented contrast/focus/labels; test with axe-core and keyboard-only flows. Avoid decorative images that hide or replace source text.

Homepage structure: clear hero, headline that this site is built with Sedrava, concise explanation, 3-4 live example entry points, docs navigation, current stable and preview release labels, GitHub and getting started. Include a build provenance link.
